## Context
Fatih Notion'u Claude uygulamasından MCP ile yönetiyor ve aynısını Unfurl için istiyor (2026-11-26): "planı haftaya pazartesi başlat", "Toolbox bloğunu ekle", "şu görevi done yap", başvurulara not ve sonraki adım. Kararlar (Fatih, 2026-11-26): **Learning + Başvurular**, toplu değişikliklerde **önizleme + onay**. Deploy yok (D-155): sunucu yereldir, Claude Desktop (ve Claude Code) başlatır. Anthropic API kullanılmaz (D-150): Claude, Fatih'in kendi aboneliğiyle çalışır.

SPEC §9'daki asistan araçları ve kuralları (silme yok, 2'den fazla kayıtta `propose_*` + onay, `user_id` oturumdan) bu sunucu için de geçerli; araç adları oradan alınır.

İki milestone (her biri ayrı PR): **I107a Learning**, **I107b Başvurular**.

### Kabul kriterleri (I107a)
- Claude Desktop ayarına eklenen tek bir komutla Claude, kişisel ortamın Learning verisini okuyabilir ve değiştirebilir.
- Araçlar sadece verilen kullanıcının verisine dokunur; hiçbir araç silmez.
- 2'den fazla kaydı değiştiren her işlem önce bir önizleme (değişiklik sayısı, örnekler, ilk/son tarih) döner ve sadece `apply_changes` ile uygulanır; uygulanan set 24 saat içinde `undo_changes` ile geri alınır.
- Doğrulama formlarla aynı (D-094: tarih aralığı, dakika, başlık, URL).
- Testler gerçek MCP istemcisi olmadan, araç fonksiyonlarını doğrudan çağırır.

### Kabul kriterleri (I107b)
- Başvuruları listeleme ve okuma; not ekleme, sonraki adım, mülakat ve durum değiştirme (SPEC §9 araçları, AI olanlar hariç). Durum değişikliğinin yan etkileri (belge kilidi, timeline) uygulamanın kendi servisleriyle aynı.

## Kararlar (DECISIONS'a, D-191'den başlar)
- **D-191 · Sunucu uygulamanın içinde, Docker üzerinden stdio (Claude önerir).**
  - **Karar:** `app/mcp_server.py`, resmi `mcp` Python SDK'sı (FastMCP, stdio). Claude Desktop onu şu komutla başlatır: `docker exec -i unfurl-personal-app python -m app.mcp_server --email <e-posta>`. Sunucu uygulamanın servislerini ve veritabanı bağlantısını doğrudan kullanır; HTTP API'si ve token yok. Kullanıcı başlangıçta e-postayla bir kez bulunur, her araç onun `user_id`'siyle çalışır (model `user_id` vermez). App container'ına sabit ad: `container_name: ${UNFURL_PROJECT:-unfurl-personal}-app`. Geliştirmede: `uv run python -m app.mcp_server --email …` (dev veritabanı). stdout sadece MCP protokolü içindir; log'lar stderr'e.
  - **Gerekçe:** Docker'a erişebilen biri veritabanına zaten erişebilir; token, yeni API ve Settings ekranı bu yerel kullanımda ek güvenlik getirmez, sadece iş ve yeni bir saldırı yüzeyi getirir.
  - **Alternatifler:** Ayrı süreç + `/api/mcp/*` JSON API + kişisel token (Settings'te oluştur, eklenti gibi): deploy sonrası uzak connector için gerekli olacak, şimdi değil. Notion gibi uzak MCP (claude.ai web/mobil): deploy + OAuth (D-155 ile çelişir).
- **D-192 · Yeni bağımlılık `mcp`.** Resmi Model Context Protocol SDK'sı (Anthropic/MCP projesi). Sürüm `uv.lock`'ta sabit; Dependabot izler.
- **D-193 · Önizlemeli değişiklikler: PendingChangeSet (SPEC §5.9c) şimdi, MCP için.**
  - **Karar:** Tablo `pendingchangeset`: `user_id`, `source` ("mcp"; ileride "assistant"), `kind` (learning_plan / application), `changes` JSON (`[{op, target_id, before, after}]`), `summary` (önizleme metni), `status` (pending / applied / discarded / undone), `created_at`, `applied_at`. `thread_id` şimdilik yok (asistan V2'de eklenir). Pending set 1 saat, Undo 24 saat geçerli. Uygulama sırasında her hedef `user_id` ile tekrar okunur ve `before` hâlâ aynıysa değişir (karşılaştır-ve-yaz); değilse o satır atlanır ve sonuçta sayılır. Migration `0022`.
  - **Alternatifler:** Önizlemeyi MCP sürecinin belleğinde tutmak (Claude Desktop yeniden başlayınca kaybolur, Undo yok).
- **D-194 · I107a araçları.**
  - Okuma: `get_learning_plan` (hedefler + ilerleme, bugün/bu hafta/gecikmiş, seri, haftalık saat), `list_tasks` (hedef, tarih aralığı, açık/bitmiş, metin; en fazla 200 satır, sayfalı).
  - Tek kayıt yazma (doğrudan): `create_learning_goal`, `add_task`, `update_task` (başlık/tarih/süre/link), `set_task_done`.
  - Toplu: `propose_learning_changes` (op'lar: `move` tarih, `shift` gün kadar kaydır (filtreyle: hedef, tarih aralığı, sadece açık), `add` çoklu görev, `update`, `complete`) → önizleme + `change_set_id`; `apply_changes(change_set_id)`; `undo_changes(change_set_id)`; `discard_changes`.
  - Silme aracı yok. 2'den fazla kayıt etkileyen bir istek tekli araçlarla gelirse araç reddeder ve `propose_learning_changes`'e yönlendirir (sunucu sayar, modele güvenmez).
- **D-195 · I107b araçları.** `list_applications` (durum, metin, arşiv dahil değil), `get_application`, `add_application_note`, `set_next_action`, `schedule_interview`, `update_application_status` (servisin kendi kuralları: kilit, timeline, Undo yok → bu yüzden tekil ve açık onaylı); toplu başvuru değişikliği `propose_application_changes` ile.

## Riskler
- **Model yanlış toplu değişiklik önerir:** önizleme + onay + 24 saat Undo; sunucu sayar.
- **Claude Desktop config'de e-posta:** kişisel veri ama yerel dosya; token/şifre yok.
- **stdio'ya log yazmak protokolü bozar:** test.
- **Container adı değişikliği:** kişisel ortam bir kez yeniden oluşturulur (veri volume'da, D-190).

- **(Blocker) Tekli araçlarla kuralı aşmak:** model `update_task`'i art arda çağırabilir. → "Sorular" 2.
- **(Blocker) Yarım uygulama:** servis fonksiyonları kendi commit'ini yapıyor. Apply, Undo ve set'in `status`/`applied_at` güncellemesi **tek transaction**: change_set_service commit etmeyen yardımcılarla doğrudan yazar; yarıda hata enjekte eden test.
- **Saat dilimi:** her araç `clock.use_timezone(user.timezone)` içinde (D-186 gibi); gece 23:30'da UTC dışı kullanıcı testi.
- **Shift (30 gün kuralı):** propose anında `shift` somut `move` satırlarına açılır (önizleme ve karşılaştır-ve-yaz kesin, §5.9c op'ları aynı). Sadece açık görevler; bitmiş görevler asla taşınmaz (D-095). N −30…+730. Apply'da tarih kuralı tekrar kontrol edilir; Undo kontrol etmez (sadece eski hâli geri koyar). Aralık dışı satırlar → "Sorular" 3.
- **Undo:** `after` ile karşılaştırır; `complete` ve geri alması `set_done` ile (StudyLog ve `units_done` doğru). `add` geri alması → "Sorular" 4.
- **Sınırlar ve temizlik:** set başına ≤ 1.000 değişiklik, kullanıcı başına ≤ 10 pending set, `changes` JSON ≤ 1 MB; 1.000 görev sınırı apply'da tekrar. Süreler UTC (`utcnow`, `as_utc`). Süresi dolan pending set'ler ve 30 günden eski applied/undone/discarded set'ler propose sırasında silinir (kullanıcının kendi set'leri).

Başlangıçta `sys.stdout` stderr'e yönlendirilir, MCP orijinal stdout'u kullanır (console e-posta backend'i stdout'a yazıyor). `app.main` import edilmez (scheduler başlamaz). Subprocess testi: geçici SQLite ile `python -m app.mcp_server` + `initialize`, stdout'ta sadece JSON-RPC. SDK'nın bellek içi istemcisiyle araç kaydı ve şema testi.

## Fatih'in kararları (2026-11-26)
1. **Onay:** Claude Desktop'un araç izni. `apply_changes` ve `undo_changes` için asla "Always allow" denmez (DEVELOPMENT.md); okuma araçları `readOnlyHint`, yazma araçları `destructiveHint` ile işaretlenir. Elicitation yok.
2. **Tekli yazma sayacı yok.** Her tekli yazma Claude Desktop'un iznine kalır. Bu, CLAUDE.md'deki "2'den fazla kayıt → önizleme" kuralının MCP için bilinçli bir istisnası: sunucu tek çağrıda 2'den fazla kaydı değiştiren isteği yine reddeder, ama art arda tekli çağrıları saymaz (D-193'e kabul edilen risk olarak).
3. **Kaydırmada aralık dışı satırlar** atlanır ve önizlemede ayrıca listelenir; kalanlar uygulanır. Apply'da tekrar kontrol: o an aralık dışına düşen satır da atlanır ve sonuçta sayılır.
4. **Undo, aynı set'in eklediği görevleri** kaldırabilir, sadece o arada değişmemişlerse (StudyLog'u yok, başlık/tarih/süre/link/done `after` ile aynı). "Asistan silmez" kuralının tek, yazılı istisnası.
